## 0. 判读规则

1. 表中每一行是**证明责任**，不是已发生事实。当前没有任何一行被演练或执行。
2. 一个场景通过只在其声明的 T 层与 L 层内成立，不得跨层外推。T3/T4 的通过永远不能读成 L3/L4。
3. "禁止解释"列具有阻断效力：出现该解释即判该场景 FAIL，即使预期行为本身看起来发生了。
4. 证据必须可复算：时间戳、事件 ID、digest、epoch、占用快照缺一即视为未采集，不得用叙述性文字补位。
5. 只写角色代号与逻辑标识，不写主机名、IP、证书、令牌、设备序列号。
6. 恢复类场景未演练时，唯一允许的表述是"未验证恢复能力"。写入任何 RPO 或 RTO 数字都属越界。

### 2.1 P-07 断线续跑的三个独立状态

必须分别记录，禁止折叠为一个"在线/离线"开关：

| 维度 | 字段 | 断线时的正确值 | 常见错误值 |
|---|---|---|---|
| 通信可见性 | `communication_state` | `OFFLINE` 或 `STALE` | 顺手改成 `DISCONNECTED` 并连带改占用 |
| 设备独占 | lease `occupancy_state` | `OCCUPIED` | `IDLE`（把租约过期误读为所有权到期） |
| 执行许可 | `execution_permit` | `GRANTED` | `REVOKED`（把失联误读为撤回） |

判读要点：租约线协议状态 `expired` 只表示续约截止，不是设备所有权到期，也不是 run 失败。断线期间节点本地继续计时、继续 spool，重连后不得因时钟推进而延长租约。

### 2.2 P-08 STOP-first 的六步顺序证据

顺序本身是判定对象。证据必须能证明每一步的**时间先后**，而不仅是"六件事都做了"。

| 步 | 动作 | 可证伪的证据 | 常见伪造形态 |
|---|---|---|---|
| 1 | 识别并优先处理待送达 STOP | 控制面排队 STOP 的 `stop_id` 与节点 ACK 时间戳 | 只给 ACK，不给排队记录 |
| 2 | 停止后续测试动作，已执行动作保持历史 | 动作序列在 STOP 后无新增，历史不被改写 | 补传时顺带删除后续动作 |
| 3 | 补传本地消息、日志、异常、证据 | spool 前后条目数与 `backfill:{node_id}:{message_id}` 计数 | 只报"已补传"无计数 |
| 4 | 按标识去重 | 重复键命中数与写入数之比 | 有补传记录但无去重统计 |
| 5 | 核对位置、设备、lease/epoch、占用 | 对账差异表，含差异项与处理 | "对账通过"一句话 |
| 6 | 对账完成后恢复正常领取 | 首个新 Job 时间晚于对账完成时间 | 新 Job 时间早于对账 |

硬规则：迟到的 STOP 不改写已执行动作历史；重传不得触发重复执行；再次执行必须由 Linux 显式创建新 attempt/run。

### 2.3 P-14 控制面恢复的顺序与禁写

| 阶段 | 必须先完成 | 完成标志 | 顺序错误的后果 |
|---|---|---|---|
| 1 数据库 | 连接、迁移版本、事务可用 | 迁移版本与冻结件一致 | 按内存或缓存重建状态，产生幽灵 run |
| 2 manifest/摘要 | 证据索引与 digest 重算 | 重算一致率与差异清单 | 把未核验摘要当已验证 |
| 3 占用对账 | task/run/device occupancy 差异 | 差异表清零或全部挂起 | 重复派发，导致重复设备动作 |

附加禁止：恢复期间不得创建新 task/run；不得用新 ID 绕过旧幂等键；恢复后旧 epoch 回执只作历史事实，不得取得执行权。

### 2.4 释放三前置的独立判定

| 前置 | 定义 | 不满足时 | 不得用它替代 |
|---|---|---|---|
| `local_stop_confirmed` | 本地执行已停止 | 保持占用 | 控制面下发 STOP 的 ACK |
| `safe_cleanup_done` | 设备已安全清理 | `quarantined` | "进程已退出" |
| `occupancy_reconciled` | 占用已对账 | 保持占用 | "释放请求已提交" |

释放**不需要**：GB 级日志归档完成、证据最终定稿、正式判定完成。三者独立跟踪，释放后证据仍可继续上传与复核。

## 3. 五轴、OFFLINE 组合与释放的分离

### 3.1 正式 PASS 的精确元组

```text
execution_status    = COMPLETED
validity_status     = VALID
business_verdict    = PASS
evidence_status     = COMPLETE
verification_status = PASS
mode                = formal
decision            = PASS
formal_pass         = true
failure_class       = none
denominator.formal_denominator = true
```

十项缺一不可。只满足前五行只能写"轴一致"，不得写正式 PASS。派生顺序先命中先返回：非 formal → `NOT_APPLICABLE`；批准/冻结/租约不符 → `BLOCKED`；安全或人工停止 → `STOPPED`；证据不完整或摘要失败 → `BLOCKED/invalid-evidence`；复核未通过 → `NEEDS_REVIEW`；全部前置成立 → `PASS`；有效失败 → `FAIL`。

### 3.2 OFFLINE 与五轴的组合

| 组合 | 五轴表达 | 正式分母 | 说明 |
|---|---|---|---|
| 断线但本地跑完且证据完整 | COMPLETED / VALID / 按业务 / COMPLETE / PASS | 可计入 | 断线不改变五轴，只改变可见性 |
| 断线且本地安全停止 | ABORTED / UNKNOWN / NOT_EVALUATED / 视情况 / NOT_RUN | 不计入 | `decision=STOPPED` |
| 断线且证据未补传完 | COMPLETED / VALID / NOT_EVALUATED / INCOMPLETE / NOT_RUN | 不计入 | 补传完成前不得计分 |
| 恢复后对账发现旧 epoch 污染 | 按对账结论回退到 BLOCKED | 不计入 | 不得把对账前状态当终态 |
| 清理失败进入隔离 | 其余轴不变 / `NEEDS_REVIEW` | 暂不计入 | 隔离不等于证据失效 |

关键结论：`OFFLINE` 是可见性状态，不是判定轴。任何把 `OFFLINE` 直接映射为 `ABORTED`、`FAIL` 或 `INCOMPLETE` 的实现都是 P0 语义缺陷。

### 3.3 释放不等于 PASS，PASS 也不要求已释放

| 问题 | 规则 |
|---|---|
| 设备释放是 PASS 前置吗 | 不是，PASS 不要求设备已释放 |
| 缺 `cleanup_receipt` 等于证据不完整吗 | 不等于，只表示释放无法确认，设备保持占用 |
| 释放是否等于验收通过 | 不等于，释放是资源事实，验收是范围结论 |
| 正式 PASS 是否等于可发布 | 不等于，发布需 DG10、发布包、回滚包与单独授权 |
| 验收通过是否等于对外交付 | 不等于，交付需移交清单与支持边界 |

四层分离：正式 PASS 是样本级结论，验收通过是范围级结论，发布是运营决定，交付是合同或移交决定。任何一层都不得替代另一层。
