## 0. 判读规则

1. 命令是目标命令，不是已执行事实。根锁文件、`tools.*`、`tests/**`、Playwright 配置与 `lstest` 由 W0/W5/W8 建立；未建立前只能登记为计划命令。
2. 任一层级结论只在其声明的层级内成立，不得跨层外推，不得"按最乐观值解释"。
3. T 表示测试活动，L 表示证据可证明的强度。两者不是同义词：T 说做了什么，L 说能证明什么。
4. 一个 `run_id` 只允许一个 `mode`；`mode`、层级、验收级别三者不一致时判定直接 `BLOCKED`。
5. 没有证据目录、没有可复算 manifest、没有独立复核签署，一律不得写 PASS。
6. 本文与 `phase4-acceptance-plan.md` §3 冲突时，以 P4-08 冻结件为正本；冲突本身登记为缺口。

## 1. T1 至 T6 测试层

| 层 | 边界 | 目的 | 环境与真机 | 目标命令 | 证据 | 不证明 |
|---|---|---|---|---|---|---|
| T1 单元 | 单个函数或类，无 IO | 判定规则、分母、状态机、幂等键、权限函数自洽 | 本地，无 DB，无真机 | `uv run pytest tests/unit -q` | 覆盖率报告、边界用例清单、失败用例清单 | 模块协作、契约一致、真实链路 |
| T2 契约 | 接口与数据结构，无业务实现 | OpenAPI、schema、事件 envelope、Job/Lease/STOP/Receipt、manifest 形状一致 | 本地 + 假对象 | `uv run python -m tools.contract_check` + `uv run pytest tests/contract -q` | 契约一致性报告、schema 校验日志、拒绝路径记录 | 集成行为、设备可用 |
| T3 集成 | 控制面模块与真实依赖 | 事务、唯一约束、outbox、租约与占用在并发下成立 | 本地多进程 + PostgreSQL 16 | `uv run pytest -m integration -q` | 集成报告、故障注入记录、迁移前向修复记录 | 真实音频、语音业务 |
| T4 模拟 E2E | 假节点全链路 | 门禁、断线、STOP-first、重连对账、恢复顺序正确 | 假节点，无真机 | `uv run pytest tests/e2e -q` | 模拟运行记录、假回执、注入异常时间线 | 真实设备、真实时序、真实释放 |
| T5 真机烟测 | 节点 + 设备 + 端点 + 证据链路 | 链路能跑通，证据能被采集与校验 | 真实节点与 DUT，`mode=smoke` | `uv run pytest tests/smoke -q --run-real-node` | 独立 `run_id` 的烟测证据、端点快照、清理事实 | 正式样本有效性、正式 PASS |
| T6 正式验收 | 正式样本 + 五轴 + 复核 + 报告 | 批准边界内判定有效且可复算 | 真实节点与 DUT，`mode=formal` | 按 `phase4-acceptance-plan.md` §8.3 第 5 至 7 步执行 | 正式证据、五轴判定、复核记录、报告 | 其他设备、固件、长期稳定性 |

### 1.1 T1 与 T2 的证据格式

T1 的最小单元是"一个不变量 + 一个通过用例 + 一个拒绝用例"。只跑 happy path 不算通过。覆盖率阈值未定（见 §5 G3），当前只能定性描述覆盖对象，不得写百分比承诺。

T2 必须包含拒绝路径：未知 schema 版本、未知枚举、越权字段、重复幂等键、缺必填字段。契约校验只证明形状，不证明语义；语义由 T1 与 T3 承担。

### 1.2 T3 与 T4 的边界

T3 允许真实 PostgreSQL，不允许真实节点与真实设备。T4 允许假节点与受控故障注入，不允许把模拟回执写成真实设备事实。T4 的"通过"只表示逻辑顺序正确，不表示设备会按该顺序响应。

T4 必须覆盖六类异常：断线、重连、待处理 STOP、旧 epoch、重复送达、控制面重启。每类都要有独立 case 与独立时间线，不得用一次运行覆盖多类。

### 1.3 T5 与 T6 的硬隔离

1. T5 与 T6 必须是不同 `run_id`，且 `mode` 分别为 `smoke` 与 `formal`。
2. T5 样本永不进入 T6 分母；烟测证据只支撑 L3。
3. T6 的每个 case 必须能回溯到 Task、Revision、Run、Attempt、Case、Evidence 与规则版本。
4. 任一层发现 P0 缺陷立即停止后续层，不以"先跑完再修"替代阻断。
5. 人工喊测、主观体验记录只作 `human_note`，不产生自动 PASS。

## 2. L0 至 L5 证据层

| 层 | 证明什么 | 必需证据 | 不证明什么 | 典型门 |
|---|---|---|---|---|
| L0 文档契约 | 字段、状态、口径、版本一致 | 评审记录、契约清单、版本哈希 | 系统可运行、设备可用 | DG3、DG4 |
| L1 静态验证 | 无硬件逻辑自洽，类型与规范通过 | lint、typecheck、schema 校验、preflight 日志、T1/T2 报告 | 模块协作、真实链路 | QG-W0 至 QG-W4 |
| L2 模拟链路 | 门禁、判定、断线、恢复逻辑正确 | T3/T4 报告、注入异常记录、假节点回执、manifest | 真实音频、真实时序、真实释放 | QG-W2、QG-W3、QG-W7 |
| L3 真机烟测 | 节点、设备、端点、采集、清理链路可跑通 | 独立 smoke run、执行日志、串口日志、原始音频、端点快照、清理事实 | 正式样本有效性、正式 PASS | DG8、P6-03 |
| L4 正式采样 | 批准边界内判定有效，Linux 可独立复算 | L3 链路的正式 run、逐 case 五轴、manifest 复算、复核记录、异常事件 | 其他设备或固件成立、长期稳定 | P6-04 |
| L5 端到端场景 | 业务闭环可用，第二任务可复用 | L4 全部 + 第二任务复用记录、报告、知识审阅记录 | 跨项目泛化、未纳入设备 | P6-05 |

### 2.1 层级不是评分，是门

L0 与 L1 只回答"说得对不对、写得自洽不自洽"。L2 只回答"逻辑在模拟下对不对"。L3 只回答"链路能跑通"。L4 才回答"判定在正式样本上成立"。L5 只回答"第二个任务能复用"。

因此 L2 通过不意味着可以少做 L3，L3 通过不意味着可以跳过 L4 的复核。层级只能顺序达成，不能合并达成。

### 2.2 证据目录

验收阶段路径：`docs/delivery/evidence/phase4/<level-id>/<ac-id>/<UTC-timestamp>-<short-ref>/`。

每个目录至少包含 `manifest.json`、`commands.log`、`result.json`、`junit.xml`（无测试写 `N/A`）、`hashes.sha256`、`review.md`、`redaction-check.txt`。`manifest.json` 必含 gate、item_id、命令、环境摘要、结果、reviewer、UTC 时间。

原始音频、原始串口、原始设备日志不进 Git；评审件与 manifest 索引可进 Git，且只能新增更正项，不得删除或原地覆盖。

## 3. T 与 L 映射矩阵

| 测试层 | 可支撑的最高证据层 | 允许的运行模式 | 永久禁止 | 计入正式分母 |
|---|---|---|---|---|
| T1 | L0、L1 | `static` | L3 至 L5、T5/T6 | 否 |
| T2 | L0、L1 | `static` | L3 至 L5、T5/T6 | 否 |
| T3 | L2 | `static`、`smoke`（逻辑侧） | L3 至 L5 | 否 |
| T4 | L2 | `smoke`（模拟烟测） | 以模拟结果替代 T5 | 否 |
| T5 | L3 | `smoke` | L4、L5、正式判定 | 否 |
| T6 | L4，补充后可达 L5 | `formal` | 以 T5 结论替代 T6 | 满足全部前置后可计入 |

矩阵读法：格子给的是上限，不是默认值。T6 若缺复核记录，只能停在"证据存在"，不能写成 L4 达成。

越级与混用的典型错误：

1. 用 L0 至 L2 的证据声称 L3 至 L5 完成。
2. 用 L3 烟测样本拼 L4 正式分母。
3. 用节点自报完成替代 Linux 独立复核。
4. 用远程按需读取成功替代归档或备份。
5. 把一个 `run_id` 同时当 smoke 与 formal 使用。

## 4. 进入与退出准则

### 4.1 进入

| 层级 | 进入条件 |
|---|---|
| T1/T2 | 代码可导入，规则版本固定，契约候选可校验 |
| T3 | T1/T2 通过，测试库可用，迁移可执行 |
| T4 | T3 通过，假节点可注入故障，STOP 队列可观测 |
| T5 | 静态检查通过，节点心跳稳定，交互会话可用，端点一致，D: 容量高于保护阈值，必要日志可读，待处理 STOP 已清空，无其他任务持有租约 |
| T6 | T5 通过且证据完整，修订已批准，样本规则已批准，资源重新检查通过，无待处理 STOP 或残留占用 |
| L5 | L4 通过，第二任务已批准并可执行 |

任一项不满足即不得进入 T5；T6 还必须满足 T5 通过、修订批准、资源重新检查通过。顺序不可倒置：不得先跑正式采样再补烟测，不得用 T4 结果替代 T5，不得用 T5 结果替代 T6。

### 4.2 退出

退出条件是"每个计划用例都有结论"，不是"每个计划用例都通过"。成立需同时满足：

1. 计划用例执行完毕，或有明确无效分类与原因。
2. 必要证据可校验，或明确标记 `UNVERIFIED`/`INCOMPLETE`。
3. 判定可复算，规则版本可查。
4. 未解决项已登记，含责任方与解除条件。
5. 失败用例已按 P0 至 P3 分级，P0 未关闭则不得签收。

### 4.3 fail-closed 规则

| 情形 | 处理 | 不得做的事 |
|---|---|---|
| 缺批准、批准快照不匹配、边界未冻结 | `BLOCKED` | 先执行后补批准 |
| 租约或 epoch 不符、设备占用冲突 | `BLOCKED` | 换新 ID 绕过幂等 |
| `mode` 缺失、未知或与层级不符 | `BLOCKED` | 按 formal 解释 |
| 必需证据缺失、摘要不符、来源或关联冲突 | `BLOCKED/invalid-evidence` | 用其他 run 的证据替代 |
| 必需日志不可读 | `UNVERIFIED` 或 `INCOMPLETE` | 判 PASS，或猜测内容 |
| `verification_status != PASS` | `NEEDS_REVIEW` | 口头宣布通过 |
| 存在未处置阻断异常 | `NEEDS_REVIEW` | 只看业务结果而忽略异常 |
| 枚举或 schema 版本未知 | `NEEDS_REVIEW` 或拒绝 | 猜测为成功 |
| 清理失败或占用不确定 | `quarantined` + `NEEDS_REVIEW` | 释放后继续派发 |

判定派生按先命中先返回：非 formal → `NOT_APPLICABLE`；批准或租约不符 → `BLOCKED`；未开始 → `NOT_EVALUATED`；安全或人工停止 → `STOPPED`；基础设施故障 → `BLOCKED/infra-error`；输入无效 → `INVALID`；环境阻塞 → `BLOCKED`；证据不完整 → `BLOCKED/invalid-evidence`；复核未通过 → `NEEDS_REVIEW`；阻断异常 → `NEEDS_REVIEW`；全前置成立 → `PASS`；有效失败 → `FAIL`；其他 → `NEEDS_REVIEW`。

正式 PASS 只认精确元组：`COMPLETED / VALID / PASS / COMPLETE / PASS`，且 `decision=PASS`、`formal_pass=true`、`failure_class=none`、`denominator_eligible=true`。缺任一字段只能写"轴一致"。

设备释放不是 PASS 前置，缺 `cleanup_receipt` 不等于证据不完整。发布、验收通过、正式 PASS、对外交付是四个不同决定，不得互相替代。
